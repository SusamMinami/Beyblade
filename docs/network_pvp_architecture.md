# PVP：产品方向、架构与接入缺口

核对：2026-09-30。合并原网络产品方案与混合同步提案。
**当前游戏是本地对战；本文的正式积分、排位与服务器能力是目标，不是已上线功能。**
本次未部署或公网联调。版本由 [确定性同步](deterministic_battle_sync.md) 维护，
端点与开发方法由 [Worker 指南](../scripts/server/cf_worker/README.md) 维护。

## 已确认方向

- 异步积分赛决定同段位内积分/排名；同步排位决定段位。
- 两种正式比赛均为三局两胜，先两胜立即结束；本地故事单局不因此改变。
- 匹配同段位且积分接近的对手，积分赛优先提供略高积分目标。
- 异步赛前只展示外观，赛后开放完整零件和 DIY 配置。
- 首发中国地区；游客可体验积分赛但不保存积分，不进入排位。
- 异步防守采用“输入录像 + 确定性策略接管”的混合幽灵。
- 正式方案以 Nakama 管理账号/匹配/赛季，Godot headless 提供权威模拟。
  Cloudflare 是可选入口、中继与回放存储，不代替权威求解器。

## 当前实现矩阵

| 能力 | 代码事实 | 接入缺口 |
| --- | --- | --- |
| 双方发射、双输入、固定帧 | Web/Godot 共享 v6 已有 | AI 便利入口仍保留；不是彻底剥离的输入源架构 |
| 完整恢复 | Web `exportState/restoreState`，Godot `export_state/restore_state` | 诊断快照和旧网络编码不能代替完整格式 |
| 本地回放 | Web `battle-replay.js` 工具；Godot `BattleSession.local_replay` 记录 | Web 主游戏尚未接入玩家回放库；没有正式服务端验算器 |
| 会话 | Godot 战斗页使用 `BattleSession`；Web 主游戏直接使用求解器 | 网络入口尚未贯通 |
| 跨端规则 | 九组真实 v6 对局与双向恢复已有阶段证据 | 不等于所有设备位级一致或弱网联机通过 |
| FrameSync / AsyncVerify | 两端 Provider、Local/WS Transport 代码存在 | 仍是旧 `2026.07.21-bin` 协议，明确拒绝 v6 |
| Worker | 房间、匹配中继与 R2 上传接口存在 | `accepted` 只代表存储；没有权威重演和正式积分结算 |
| StateSync / 账号 / 赛季 | 长期方案 | 没有完整交付或公网运行证据 |

不要重复开发已存在的恢复 API，也不要只改版本号跳过网络兼容检查。

## 三层职责

```text
界面/输入 → BattleSession（准备、发射、运行、结束）
                ↓
          SyncProvider（如何推进规则）
                ↓
          Transport（Local / WebSocket；其他传输按需）
```

| 模式 | 推进方式 | 适用边界 |
| --- | --- | --- |
| FrameSync | 中继双方逐帧输入，客户端运行相同规则 | 本地双端与技术封测；哈希一致不能独立证明结果合法 |
| AsyncVerify | 本地模拟并记录回放，服务端从初态重演 | 正式积分以验算结果为准；上传成功不能先发正式积分 |
| StateSync | 服务端固定步长模拟，客户端发送输入并插值 | 正式排位目标；需运行权威进程的宿主 |

输入源可来自触控、键盘、幽灵或网络；渲染只消费状态。
本地经济继续服务单机。正式比赛须由服务器确认所有权、配置、规则、种子、
输入、胜负与奖励；本地金币和可调参数不能直接成为排位依据。
旧方案中的“乐观积分 + 10% 抽验”未被采用为正式结算规则。

## 数据与版本契约

以下是目标模型，**不是现有 WebSocket 字节布局**。当前 HTTP 为 JSON、
WebSocket 为二进制 v2，量化与批次直接使用三端协议源文件。
当前 `INPUT_BATCH_SIZE = 6`，不要抄用旧文档的三帧或方向 int16 表。

| 对象 | 必须保存的内容 |
| --- | --- |
| Manifest | 协议、求解器、内容清单哈希、调参配置、固定步频 |
| BuildSnapshot | 所有者、槽、五件 ID、DIY、发射器、保养、外观与配置哈希 |
| Ticket | match/series ID、模式/地区、种子/地图、双方配置版本、时间窗、nonce、签名 |
| LaunchCommand | slot、力度、高度、方向、倾角的规范化命令 |
| InputFrame | frame、slot、sequence、control_x/y、flags |
| ReplayEnvelope | manifest、公开票据、双方初态/发射、逐帧输入、完整检查点、最终结果/哈希 |

服务器由版本化正式零件数据重算属性，不信任上传的攻击、质量或惯量。
完整检查点须包括旋转相位、轴状态、结构扇区、接触历史、下落和供能统计；
显示用 snapshot 不能用于续算。v6 恢复校验规则见确定性文档。
旧哈希模块不能自动用于 v6；规范化字段、数值精度、UTF-8 与字节样本需重新验收。
发布后的规则保持可追溯，旧回放在审计窗口内使用对应版本重演。

异步赛前隐藏配置只约束正常 UI：本地模拟需要足够战斗数据，
不承诺对逆向客户端绝对保密。强保密需要服务端执行交互模拟。

## 异步积分赛目标流程

1. 验证所有权后发布不可变的防守配置、发射与输入录像版本。
2. 录像记录距离、相对方向、半径、转速及危险等级等情境。
3. 发挑战票据并冻结系列赛对手、规则与种子；后续改装不影响已发票据。
4. 情境匹配用录像，偏离、结束或缺帧时由确定性策略接管。
5. 提交完整回放；服务端从第 0 帧重演，按 `series_id + nonce` 幂等结算。
6. 结算后展示完整配置；游客票据 `unrated_guest` 不写积分榜。

候选计分公式仍为提案：
`max(原积分 + 基础增量, 对手积分 + 1)`；
失败不加分、防守方不直接扣分。基础增量、重复挑战冷却、每日次数、
赛季软重置和升降段后积分处理尚待定案。
混合控制器与情境阈值必须纳入规则版本，不能读取未记录的随机数或墙钟。

## 同步排位目标流程

匹配 → 锁配置/规则 → 签发房间票据 → 双方加载与 ready → 发射窗口 →
服务端 60Hz 推进 → 小局结果 → 先两胜后冻结系列并结算。

- 客户端只决定输入和本地表现；服务端拥有最终状态。
- 输入批频、15–20Hz 快照、100–150ms 插值是待弱网测量的起点，不是当前承诺。
- 迟到输入采用上一有效值还是归零须全局统一；短断线恢复完整快照。
- 第一版目标为权威快照加插值，不把完整预测回滚设为前提。
- 重连窗口、退出处罚、AI 接管、服务器故障无效局和地图选择规则仍待定。
- 记录 RTT、抖动、丢包、迟到与校正幅度；目标中国运营商网络须真机验证。

## 接入顺序与验收

1. 冻结待联网的共享规则和配置清单；升级三端协议、完整编码和哈希，
   明确拒绝旧/非法版本、越界输入与非法零件。
2. 在现有完整状态/回放 API 上接入主游戏的记录和播放，验证落盘读取、
   从中途恢复与从零重演一致；重复固定输入回放无结果漂移。
3. 提供命令行权威验算器，对通过、非法输入、结果不一致返回明确状态/退出码。
4. LocalTransport 双客户端验证输入批次、延迟、断线与同帧状态；
   然后 Worker 本地联调，最后目标移动网络联调。
5. 实现签名票据、服务端所有权、幂等积分/奖励，再开放正式入口。
   回放上传、等待验算、验算通过、正式结算分别显示真实状态。

本地规则和回放检查已有部分覆盖；上述整条链未验收，
不能把清单全部打勾，也不因存在会话代码就宣称能联网。

## 部署边界

先本地开发，再技术封测，最后按实测选择权威主机与地区。
Worker/DO 可承接 API 与中继，R2 存回放；不将普通 Worker 当作 Godot 进程宿主。
Nakama 数据库、权威实例与存储容量按实际负载选型，不保留过时的固定云规格或免费局数承诺。
套餐、配额、DO 迁移资格和中国网络可达性均需部署时核实；官方来源集中在 Worker 指南。

当前未决事项是段位/赛季与积分公式、系列地图、断线裁决、首发 RTT 目标和部署节点。
这些决策影响正式联网，不阻止继续完善当前单机玩法。
