# 陀螺物理与可预期反馈检查

日期：2026-09-23。对象：当前 Web `2026.09.16-web-v4` 完整物理子系统及输入、渲染、音频和改装评分调用链。本文是诊断与改进建议，不表示以下改动已实现。

2026-09-24 更新：前两轮已进入 Web v5 实现，当前行为与验证见
[实现记录](physics_v5_implementation.md)。下文保持检查时的原始证据与数值，不能用于判断新版问题仍然存在。

## 结论

当前已经具备可继续演进的基础：固定步长、确定性输入、质量与轴向惯量、地面差异、五零件八扇区损伤、永久结构失衡，以及按惯量计算的有限补转。应保留这些能力和现有零件、DIY、库存及经济模型。

最先需要解决的是反馈一致性。现在玩家有可能遇到“右推却向屏幕左边走”“受损陀螺旋转到某个相位突然看起来直立”“购买页说续航提升，实际自由旋转却缩短”等现象。这些会妨碍学习操作规律。

物理模型的下一步重点是让接地点、旋转、倾斜、损伤方向共享同一套状态。现有降阶模型可以逐步补齐这些关系，无需把整个战斗替换成不可控的完整刚体系统。

所有参数和实验数据仍为游戏平衡单位；转速不表示真实 RPM，质量、惯量、长度不冒充 SI 测量值。

## 优先修正的五项实现问题

以下五项均为 P1；置信度为 10/10。音频的异常已在隔离浏览器复现，异常如何中断正式帧循环另由调用链确认。

### 1. 动态镜头与屏幕操作方向不一致

位置：[main.js](../web-prototype/src/main.js#L2135-L2139)；关联 [three-stage.js](../web-prototype/src/render/three-stage.js#L2097-L2118)。

摇杆和键盘产生的屏幕左右输入直接作为世界 X/Y 输入。标准场和复合场的镜头会跟随玩家径向绕场，镜头转到另一面后，同一个世界方向在屏幕上反向。

关键代码：

```js
const control = this._keyboardControl();
this.simulation.step(FIXED_STEP, control);
```

精确复用当前相机公式计算：玩家分别位于规则位置 `(0,+4)` 与 `(0,-4)` 时，同样世界 `+X` 位移的屏幕横向增量由 `+0.060502` 变成 `-0.060502`。这不是控制箭头单独画反；实际施力也未按镜头转换。街头、冠军、遗迹采用固定场景方位，不触发这一绕场反转。

**建议：**在输入边界将屏幕向量转换为相机地面投影的 right/forward 向量，再交给纯求解器。确定性输入记录保存转换后的世界指令。也可以固定战斗镜头方位，但应明确选择一种操作约定。

**验收：**在多个镜头方位，轻推屏幕右侧始终向屏幕右侧施力；箭头、实际加速度与录制指令一致。

### 2. 自旋会错误地改变可见倾角

位置：[three-stage.js](../web-prototype/src/render/three-stage.js#L2067-L2077)。

关键代码：

```js
model.rotation.y = state.spinPhase;
model.rotation.x = Math.cos(direction) * state.tilt;
model.rotation.z = -Math.sin(direction) * state.tilt;
```

默认 XYZ 欧拉角的组合将自旋夹在两次倾斜之间。模型自旋时，它的轴与竖直方向的夹角也发生变化。

取 `velocity=(1,1)`、求解器 `tilt=0.62`，实际 Three.js 轴倾角为：

| 自旋相位 | 可见轴倾角 |
| --- | ---: |
| 0 | 0.609731 rad |
| π/2 | 0 rad |
| 3π/2 | 0.876812 rad |

求解器认为陀螺保持约 35.5° 倾斜，画面却会经过完全直立和约 50.2° 倾斜。离地高度仍按 `cos(state.tilt)` 计算，也会与可见姿态不一致。

**建议：**分开倾斜父节点和自旋子节点，或使用明确的 `qTilt × qSpin` 组合。轴尖高度、局部损伤和接地点一起消费同一姿态。

**验收：**固定倾斜姿态扫过完整自旋周期，可见轴倾角不变；轴尖不因自旋穿地或跳高。修复渲染组合后，仍需单独建设物理倾斜方向，不能把当前速度方向近似称为真实进动。

### 3. 倾角发射的附加速度固定朝世界右侧

位置：[battle-simulation.js](../web-prototype/src/core/battle-simulation.js#L140-L143)，同类公式也在 `_applyLaunchToTop`；预览见 [three-stage.js](../web-prototype/src/render/three-stage.js#L1776-L1811)。

```js
x: Math.sin(direction) * playerSpeed + launchAngle * 0.72,
y: -Math.cos(direction) * playerSpeed,
```

标准配置、力度 0.86、高度 0.45、倾角输入 1：

| 发射方向 | 实际初速度 | 保持局部手势、整体旋转后的预期 |
| --- | --- | --- |
| 0° | `(0.72, -7.22638)` | 相同 |
| 90° | `(7.94638, 0)` | `(7.22638, 0.72)` |

相同倾角在一个朝向是侧推，换个朝向则变成前向加速。箭头预览又只使用 direction，未体现附加速度。预览模型的倾角与实际初始 tilt 也使用不同倍率。

**建议：**用发射局部的前向、侧向向量计算初速度；直接发射、显式命令和预览共用只读初态计算。区分发射器姿态与落地陀螺姿态，给变化一个明确过程。

**验收：**旋转整个发射设置时，初速度和姿态随之旋转；预览箭头对准实际初速度，不能只更新箭头而保留求解器中的方向偏差。

### 4. 同帧淘汰依赖检查顺序

位置：[battle-simulation.js](../web-prototype/src/core/battle-simulation.js#L793-L820)。

```js
const candidates = [
  [this.player, "enemy"],
  [this.enemy, "player"],
];
```

循环检查到第一个失败者便结束比赛。受控平地、无供能、双方相同配置与零速度，转速都从 `2.01` 经一帧降至 `1.9364606692742283`，结果固定判 `enemy` 胜。双方同帧结构失效或出界也有相同顺序问题；而超时同分又固定判玩家胜。

**建议：**先收集双方失败状态，再统一裁决。默认推荐将同帧无法区分先后的情况标为平局或重赛；如果要判断亚帧先后，需要明确且统一的接触时间算法。

**验收：**交换双方身份不改变客观胜负；双方同时停转、出界、破坏和超时同分都有明确规则。平局一旦引入，要同步任务、奖励、战报和协议的语义。

### 5. 同批风险音效可抛异常并打断刷新链

位置：[audio-engine.js](../web-prototype/src/audio/audio-engine.js#L157-L190)；调用链 [main.js](../web-prototype/src/main.js#L1843-L1861)、[帧循环](../web-prototype/src/main.js#L2138-L2155)。

```js
const now = Tone.now();
this.warningSynth.triggerAttackRelease(
  note,
  state === "critical" ? 0.12 : 0.07,
  now,
  state === "critical" ? 0.48 : 0.28,
);
```

不同风险共用同一个单声部；同一 WebAudio 时钟量子内的第二次触发会得到相同开始时间。隔离 Chrome 中连续调用真实 `playRisk("ring_out_risk","warning")` 和 `playRisk("spin_risk","warning")`，复现：

```text
Start time must be strictly greater than previous start time
```

这类事件确实可以由正常模拟同一步产生：标准场、偏心配重、seed=13 的固定输入对局第 292 步同时出现出界预警与低转速预警。正式 `_tick` 未捕获 `_processEvents` 中的音频异常，下一个 `requestAnimationFrame` 又在其后安排，因此异常会阻止后续帧调度。浏览器实验验证的是音频函数异常，未声称已录制完整游戏卡死过程。

**建议：**聚合风险提示，选择最高优先级；或使用能处理多声部/严格递增调度的实现。音频失败必须与战斗推进隔离。

**验收：**同一步多风险、多物理步集中在一渲染帧时均无异常；音频失败或关闭不改变物理结果，也不停止画面更新。

## 物理模型最值得补齐的关系

以下为后续设计方向，不能标记为现有求解器已经实现。

### A. 让损伤方向进入姿态与运动

当前 [偏心扰动](../web-prototype/src/core/battle-simulation.js#L301-L315) 只读取重心横向偏移的长度；漂移方向由时间、种子和角色身份生成。擦地漂移使用另一组时间相位。标量 tilt 表示倾斜程度，不能表示轴向、倾斜朝向或进动。

受控证据：标准配置、同初始旋转相位，分别在相反侧施加四次载荷 22：

| 条件 | 重心 X 偏移 | 结构失衡 | 0.5 秒后位置 |
| --- | ---: | ---: | --- |
| 一侧破损 | -0.009256552 | 0.636558691 | `(-0.001093147, 0.049136802)` |
| 对侧破损 | +0.009256552 | 0.636558691 | `(-0.001093147, 0.049136802)` |

两组位置、速度、倾角和转速完全相同。实验隔离了供能、地形噪声及对手碰撞。这证明当前损伤方向未进入这条漂移链，不代表真实旋转陀螺必然永远向受损一侧漂移。

**建议：**增加陀螺轴方向、倾斜变化率与有符号自旋；将本体重心偏移按旋转相位变换到世界坐标。以接地点、重心距支点高度和接触力矩决定倾斜，再加入受控的进动与耗散。稳定性应参考有效角动量 `L=Iω`，而不只依赖相对最大转速与经验稳定分。

**玩家收益：**看见某侧受撞后，可以理解接下来的摆动、擦地和掉转；通过相同场景重复操作可以学会规避与恢复。

### B. 让旋转参与擦碰，而不仅是提供分离反冲

当前 [陀螺接触](../web-prototype/src/core/battle-simulation.js#L489-L580) 主要沿两中心连线施加法向冲量。新增的齿反冲已经从旋转能量扣账，值得保留其能量约束；但没有接触点切向速度、左右旋或切向摩擦产生的旋转交换。DIY 的凸翼仍使用圆形接触包络。

**建议：**从 `vContact = v + ω × r` 求接触点相对速度，分开法向和切向冲量；切向摩擦改变双方平移及角动量，并限制总能量。先做有摩擦的圆盘接触，必要时再引入少量凸轮廓采样，使可见凸翼与碰撞法线更接近。

**玩家收益：**迎面硬撞、侧擦、追尾、同旋与反旋接触有可理解的差异，攻击角度比单一攻击分更有意义。

持续接触与“分离后再次相撞”应分开处理。现有 0.12 秒全局冷却会同时抑制伤害、失衡与碰撞事件；受控短间隔重碰中，速度已经被反弹而 hits 未增加。应限制声音/粒子频率，同时用接触阶段识别避免重复伤害。该夹具没有证明自然对局中的发生频率。

### C. 发射、惯量、地面耗散使用同一口径

当前 `maxSpinSpeed ∝ 1/√I` 大致对应固定旋转能量的发射方式；基础掉转却是直接减固定角速度，加速区又使用 `torque/I`。这使惯量对启动、耗散和供能的影响不统一。

**建议：**明确发射的能量预算，再用接地点损耗扭矩、与转速有关的阻力和结构擦地扭矩计算 `dω/dt=τ/I`。空气阻力可采用经过调优的转速函数，不需要假装具有真实材料常数。

尖端接地可逐步加入有效摩擦力矩半径、滑移速度、滚动/滑动状态与橡胶耗散。接触面积目前明确为预留参数，不能简单把库仑摩擦写成“面积越大摩擦力越大”。玩家操控可保留辅助力，但应说明其来源、抓地上限以及与转速的关系。

**玩家收益：**重外圈、橡胶尖、金属尖、扁平尖呈现一致的取舍；不能事先保证“更重一定更耐转”，但能说明哪项收益被哪项代价抵消。

### D. 边缘与地面共用几何规则

当前护圈的放行条件是外向速度 `9.2`；没有爬坡过程，是否放行也未使用接触高度、姿态或 DIY 半径。

受控调用 `_resolveArenaRim`，同位置 `x=6.71`：

- 外向速度 `9.1999`：位置修正为 `6.67`，速度反向为 `-4.783948`。
- 外向速度 `9.2001`：位置和速度保留，允许继续外移。

跨越边缘本来就可能有临界结果；问题是当前缺少可见且可学习的爬坡、速度损失和支撑变化。

**建议：**共享地面高度/法线与护圈轮廓，先增加有限高度的边缘势垒及支撑半径，再让倾斜与触地状态参与越界。零件高度若影响实战，应以轴尖接地点与装配锚点计算重心高度，避免将规则 Y 偏移误解为实际离地高度。

连续碰撞检测可在提高速度、缩小接触尺寸或发现漏碰时补入；本次没有证据表明所有普通对局已经出现穿透，不将完整 CCD 列为首轮必做。

## 用实战条件测量帮助玩家建立预期

### 评分应该和它声称表达的结果同向

[现有五项评分](../web-prototype/src/core/assembly-calculator.js#L159-L166) 是属性换算；续航只读基础掉转，耐久只读加权零件耐久，未包含所有运行时因素。

受控自由旋转使用真实遗迹场地、同满功率/零高度发射、零平移、零输入，无碰撞与补转：

| 配置 | 惯量 | 最大转速 | 续航分 | 实际停转时间 |
| --- | ---: | ---: | ---: | ---: |
| 标准 | 0.89 | 65.000 | 84.85 | 14.283 秒 |
| 仅换重型配重 | 1.03 | 60.421 | 86.87 | 13.567 秒 |

购买反馈的“续航 +2”与该标准条件下的实际自由旋转排序相反。这不证明重配重在所有战术下更差。

结构抗损也有类似偏差：仅把标准攻击环 size 从 0.78 增至 1.24，耐久分从 78.20 增至 83.36；相同载荷 20、同相位、零倾斜的单次冲击，外环最重扇区损伤却从 34.42% 增至 42.21%。实战容量考虑厚径比与凸翼集中，评分未考虑。

**建议：**复用真实求解器或共享计算函数，提供固定条件下的自由转时、滑行/制动距离、短控制脉冲偏移、等载荷抗损、区内净补转。保存场地、发射参数、输入和版本作为条件；评分仍可简化展示，但应可展开查看条件和取舍。

实验室现有风场明确是局部展示；不应为了统一报告而悄悄给战斗加入风。

### 每一种反馈应该对应真实发生的事件

建议将一整物理步的转速变化分成自然耗散、擦地、撞击与供能，而不是只显示一个混合数值。当前 `spinLossRate` 在双陀螺碰撞之前计算，不含整步所有接触损耗。

值得补齐的反馈包括：

- 新受撞部位/扇区短暂高亮，区别旧伤与这一撞的新伤。
- 滑行、抓地、持续擦地、护圈反弹采用不同且随强度变化的声音。
- 供能显示“正在供能、达到上限、净补转、仍在耗转”等实际状态。当前健康陀螺高于补转上限时也会正常掉转，不能仅凭净掉转就称为“带伤”。
- 自然停转、结构失衡、击破和超时使用各自的终结动作；不要都用同一个大撞击暗示击碎。
- 拖尾用时间戳衰减，避免其长度随刷新率改变而误导速度判断。

这些反馈必须消费求解器事件与分项数据；粒子、音频和镜头不能反向决定战斗结果。

## 建议实施顺序与验收标准

### 第一轮：保证玩家看到和操作到的东西可靠

优先处理五项 P1，再统一发射预览、配置评分与供能文案。该轮多数工作可在保留现有碰撞和零件基线的情况下完成；发射方向与裁决修改须单独标注规则影响。

验收：

1. 相机转向与发射旋转的对照测试通过；测试使用对称场地或同时变换地形，避免固定加速区破坏对称条件。
2. 固定倾角完整自旋周期中，可见轴倾角不漂移。
3. 同帧双方失败与超时同分有一致裁决；身份标签交换不偏置结果。
4. 多事件音频调度无异常，音频失败不阻断刷新。
5. 评分排序与声明的测量条件相符；不能以“理论评分”掩盖反向反馈。

### 第二轮：建立姿态、接地、旋转接触的统一状态

先明确能量/角动量与尖端接触口径，再加入方向性损伤响应和切向接触。每次只改变一条因果链，保留标准配置与现有真实部件。

验收：

1. 固定初态、相位和接触点，受力方向改变会产生对应的姿态响应；相反侧损伤不再被无条件压缩成同一漂移输入。
2. 无操控、无供能的隔离接触，总机械能不凭空增加；有碎片/场地势能时使用相同记账边界。
3. 发射输入、补转与耗散使用一致的惯量口径；不同尖端的滑行与掉转取舍可重复测得。
4. 迎面撞、擦碰、持续贴靠、撞障碍后短间隔重碰分别验证。
5. 用人类短时试玩检查是否能根据方向、地面和轴姿态预测下一小段运动；不要求预测复杂多次碰撞后的全部胜负。

### 第三轮：更真实的场地与复盘

接入地形法线、边缘支撑、装配高度与分项遥测；用固定种子、固定逐帧输入生成可对照的实验报告与短回放。

固定物理步输入在 30/60/120Hz 渲染下应得到相同结果；同时明确低性能时的时间策略。当前帧时长最多计入 0.05 秒，低于约 20fps 会让模拟慢于墙钟，不宜宣称任意设备上的同秒手势完全等价。

实际改变物理规则后，应更新 Web 模拟版本、审查金标变化并注明 Godot/Worker 未迁移范围。不能只改版本字符串宣称跨端兼容。
