# Web 场景进入耗时：诊断与优化

核对：2026-09-17。适用 `web-prototype/`，不包含 Godot。

## 结论

主要问题是首次绘制准备，以及切换页面时重复销毁和重建。
本地测试中，网络传输不是街头、冠军场进入卡顿的主要部分。
此次已实现按需加载、当前场景复用、陀螺与缩略图缓存、异步材质准备。
模型、材质效果、阴影分辨率、日夜灯光及物理配置保持原规格。

## 原因与证据

1. **文件到达不等于画面就绪。** 原实现把 GLB 加入场景后立即报告 ready，
   随后的第一帧才进行着色器编译、几何/纹理上传、阴影与反射绘制。
   街头首进基线中，ready 约 77ms，强制首帧绘制约 4652ms；
   从街头预览进入战斗，ready 约 155ms，首帧约 3013ms。
   首帧计时涵盖多种 CPU/GPU 准备，不能把全部时间都归为着色器编译。
2. **同一场景反复拆建。** `showArena()` 和 `prepareBattle()` 原先都销毁
   当前 GLB、街头积水反射、两套塑料反射探针或冠军灯组，再加载同一文件。
   浏览器文件缓存不能复用这些已释放的场景对象和材质程序。
3. **每次返回都重建陀螺和三张缩略图。** Lab/Showroom 的 refresh 及载入回调
   重复建模、渲染和 resize。普通 CPU 条件返回约 230ms；
   4 倍 CPU 限速后返回达到约 1 秒。
4. **陈列室顺带下载无关房间。** 两个实验室、两个舞台通过构造函数立即加载，
   共 4 个 GLB、7.40 MB。默认陈列室实际上只需要 1 个 GLB、1.76 MB。
   资源计时包含主线程忙碌造成的事件交付延迟，不能直接解释为纯下载耗时。

## 已实现

- 同一地图预览、进入战斗、返回预览复用 GLB、环境反射和灯组。
  每局仍创建新的参赛陀螺，清空损伤模型、碰撞效果、场景脉冲和区域显示状态。
  换另一张地图或进入改装台仍释放旧场景；没有无限增长的地图缓存。
- 陀螺模型按实际零件、涂装和 DIY 值判断是否重建。缩略图共享于实验室与陈列室，
  缓存只保留现有配置，改色/改装会失效；名称、金币与测试结果不触发重复建模。
- 实验室与展示舞台按当前选择加载；同一文件的并发加载合并。
  加载失败可重试，迟到的结果不替换新选择。锁定舞台预览不装备、不改变所有权。
- `prepare-scene.js` 使用 Three.js `compileAsync()` 准备可见材质，
  保留自定义材质代码与实际输出目标。临时材质持有待编译程序，避免用户快速切换、
  释放原材质时异步编译访问已释放对象。完成首帧提交后才报告 ready。
  这并不保证浏览器已完成屏幕合成，也不保证所有阴影、反射变体都能完全异步。
- 实验室只在拥有共享画布时 resize/绘制，避免后台实验室覆盖陈列室画布。

## 测量方法与结果

脚本：[measure-scene-loading.mjs](../web-prototype/tools/measure-scene-loading.mjs)。
隔离存档，依次陈列室→实验室→来回切换→标准地图→冠军/街头/遗迹预览与战斗。
选场后等待已有轮播滚动提交，避免把另一张地图误计为当前地图。

本机 Windows、Chrome 152.0.7977.84 Headless、NVIDIA RTX 4080 / ANGLE D3D11，
1440×1000，DPR 1；支持 `KHR_parallel_shader_compile`。
测量从操作开始到资源准备、一次实际绘制、`gl.finish()` 及两次 RAF，
用来对比可见帧路径，不是线上用户感知延迟的精确测量。
同一脚本分别取改动前和最终工作区的结果，没有在性能采样期间并行运行其他浏览器验收。

`cached.json` 是尚未加入异步材质准备的中间实验，不是最终结果。

**边界：** 这些是固定路径的单次采样，不是多次分布或 P95。
首次进入仍受驱动编译缓存与本机负载影响；不能把小幅变化视为稳定收益。
禁用 Chrome 着色器磁盘缓存并不清除所有驱动缓存。
重新加载曾经进入过的另一张地图，在普通 CPU 条件下增加了约 25–32ms
的异步准备调度时间；并非所有路径都更快。

同一浏览器进程内还执行 4 倍 CPU 限速：陈列室返回 1168→161ms、
测试室返回 999→105ms、冠军场预览到战斗 1436→910ms、
街头预览到战斗 1432→845ms。部分首次/换图路径没有收益。
这组运行已经复用较暖的驱动缓存，所以不能直接与上一表的首次进入时间比较。
CPU 限速也不等于低端手机 GPU，尚未做实体移动设备或公网慢网验证。

## 回归与画面核对

- `npm test`：29；`npm run build` 通过，保留既有 Three.js 大 chunk 提示
  （约 890 kB，gzip 267 kB）。
- 实验室 27、陈列室 25、场景/碰撞 31、街头 33、冠军场 24、
  流程 41、教学成长 57 项检查通过。
- 新增 `npm run verify:loading`：17 项，包括按需请求、缓存失效、锁定预览重试、
  共享画布归属、同场景复用、每局重置、迟到响应、编译中销毁和无未捕获异常。
- 街头、冠军场检查调整为等待异步准备结束后再统计绘制与资源，
  避免把未绘制的场景当作内存基线。反射、灯光像素变化、暂停、减少动态效果、
  日夜切换与释放后几何/纹理计数回归通过。
- 桌面及手机宽度截图与先前已提交画面对照，未发现模型、材质或布局缺失。
  动态灯光和陀螺角度的不同属于采样时刻差异；未宣称逐像素完全相同。

## 后续机会（尚未实现）

1. 在玩家阅读准备信息的空闲时间，预编译下一步实际参赛配置的材质，
   尤其是街头多灯与反射下的陀螺。需要预算、取消机制与真实设备测量，
   避免把卡顿提前到地图滚动或改装操作。
2. 进一步分析首次陈列室和街头的阴影、反射变体以及同步 GPU 上传。
   当前约 2.1 秒和 3.2 秒的首次进入仍有提升空间。
3. 公网版本测量 GLB 压缩、缓存头和资源分发；验证视觉无损的几何压缩方案。
   压缩可减少下载，但不能替代着色器和重复建模优化。
4. 在实体手机测量首次进入、显存与持续帧率，再决定是否需要可选择的画质档。
   本次没有通过减少灯光、反射、模型细节或改变物理来换取更快进入。
